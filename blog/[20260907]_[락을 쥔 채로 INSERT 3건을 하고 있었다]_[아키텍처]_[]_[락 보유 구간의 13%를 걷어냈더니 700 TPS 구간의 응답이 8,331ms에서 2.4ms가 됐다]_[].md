# 락을 쥔 채로 INSERT 3건을 하고 있었다

## 들어가며

주문 API는 이미 "맞게" 동작하고 있었다. 초과 판매가 나지 않았고, 동시성 테스트 10건이 전부 통과했다. 재고 차감은 조건부 `UPDATE`의 영향 행 수로 판정하고, 여러 상품을 차감할 때는 `productId` 오름차순으로 정렬해 데드락을 막는다.

정합성 질문에는 답이 끝나 있었다. 남은 질문은 그다음이었다.

> **정합성을 지키면서 초당 몇 건까지 처리할 수 있는가.**

부하를 걸어 보니 상한이 708 TPS였다. 그런데 흥미로운 건 상한 자체가 아니라 그 근처에서 벌어지는 일이었다. 도착률 600 TPS에서는 응답 중앙값이 6.9ms인데, **700을 걸면 서버는 592.5밖에 처리하지 못하면서 중앙값이 8,331ms가 된다.** 도착률을 100 올렸을 뿐인데 1,200배가 느려지고, 그러면서 처리량은 오히려 줄어든다.

코드는 두 군데를 고쳤다. 새 기능은 없고, 동시성 설계도 그대로다. 바뀐 것은 **락을 얼마나 오래 쥐고 있는가** 하나다.

결과는 이랬다.

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 핫스팟 상한 | 708 TPS | **887 TPS** (+25.3%) |
| 도착률 700 TPS 를 걸었을 때 — 달성 | 592.5 TPS | **700.0 TPS** |
| 〃 응답 중앙값 | 8,331ms | **2.4ms** |
| 주문 1건당 쿼리 수 | 7개 | **6개** |

락 구간에서 걷어낸 시간은 전체의 **13%**다. 그런데 응답 시간은 3,471배 좋아졌다. 이 글은 그 간극이 왜 생기는지에 대한 이야기다.

## 1. 목표를 먼저 정하면 순서가 거꾸로다

"1,000 TPS를 목표로 하자"로 시작하면 안 된다. 무엇을 고쳐야 그 숫자에 닿는지를 모르는 채로 숫자만 정한 것이기 때문이다.

먼저 그려야 하는 건 **제약 스택**이다. 요청이 통과해야 하는 관문을 위에서부터 늘어놓고, 어느 관문이 가장 좁은지 찾는다.

```
톰캣 워커 스레드 200
        ↓
HikariCP 커넥션 40
        ↓
MySQL InnoDB 행 락
```

워커 200개가 커넥션 40개를 두고 경쟁한다. 커넥션을 얻지 못한 160개는 대기한다. 그러니 병목은 스레드가 아니라 그 아래 커넥션이다. 그리고 커넥션을 쥔 40개가 **같은 상품 행**을 사려 들면, 그 아래에서 한 번 더 좁아진다. 배타 락은 한 번에 하나만 통과시킨다.

그래서 부하 형태를 둘로 나눠 쟀다.

| 시나리오 | 상품 선택 | 무엇이 드러나는가 |
|---|---|---|
| **핫스팟** | 항상 `productId = 1` | 단일 행 배타 락의 직렬화 |
| **분산** | 137개 중 랜덤 | 커넥션 풀·CPU 포화 |

한쪽만 재면 절반만 본다. 핫딜 상품에 트래픽이 몰리는 상황이 핫스팟이고, 평상시가 분산이다. 둘 다 실재하는 부하다.

## 2. 락 보유 구간을 분해한다

핫스팟 상한 708 TPS를 역산하면 락 보유 시간이 나온다.

```
1 ÷ 708 TPS ≈ 1.41ms   ← products 한 행이 잠겨 있는 시간
```

같은 상품을 사려는 모든 트랜잭션이 이 창구에 한 줄로 선다. 그렇다면 이 1.41ms 안에 무엇이 들어 있는가. `performance_schema`로 300 TPS·30초를 재서 분해했다.

| 쿼리 | 호출 수 | 평균 | 락 구간 안인가 |
|---|---|---|---|
| `UPDATE products SET stock` | 10,501 | 9.983ms | 락 **획득** |
| `INSERT orders` | 10,501 | 0.070ms | **예** |
| `INSERT order_items` | 10,501 | 0.068ms | **예** |
| `UPDATE order_items SET order_id` | 10,501 | 0.045ms | **예** |
| `COMMIT` | 10,501 | 1.084ms | **예** (커밋 완료 시 락 해제) |
| `SELECT products` | 10,500 | 0.060ms | 아니오 |
| `SELECT users` | 10,498 | 0.073ms | 아니오 |

시간순으로 그리면 이렇다.

```
UPDATE products (락 획득) ─┐
  INSERT orders              0.070ms
  INSERT order_items         0.068ms   } 코드로 걷어낼 수 있는 구간 = 0.183ms
  UPDATE order_items(FK)     0.045ms
  COMMIT                     1.084ms   ← 락 안에서 잰 것들(1.267ms)의 86%
(락 해제) ─────────────────┘
```

역산한 창구 1.41ms와 락 안에서 실제로 잰 합 1.267ms 사이의 차이는 측정에 잡히지 않는 구간(네트워크 왕복, 커넥션 반납 등)이다. 어느 쪽을 분모로 잡든 결론은 같다 — **코드로 걷어낼 수 있는 건 0.183ms뿐이고, 나머지는 커밋이다.**

두 가지가 눈에 걸린다.

**첫째, `UPDATE products`의 9.983ms는 쿼리가 느린 게 아니다.** 같은 환경의 저부하 구간(400~600 TPS) 응답 중앙값이 2.3ms인데, 그 안에 든 쿼리 하나가 10ms일 수는 없다. 이 숫자는 **락 대기를 포함한 값**이다. 병목의 원인이 아니라 병목의 결과다.

**둘째, 우리가 쓴 적 없는 쿼리가 하나 있다.**

```sql
UPDATE order_items SET order_id = ? WHERE id = ?
```

주문 1건당 정확히 1회, 그것도 **락을 쥔 채로** 나가고 있었다.

## 3. 개선 A — 주문 저장을 재고 차감 앞으로 옮긴다

락은 재고 차감에서 잡히고 커밋에서 풀린다. 그렇다면 주문 저장을 그 앞으로 빼면 INSERT들이 락 구간 밖으로 나간다.

```
변경 전:  쿠폰 소모 → 재고 차감 → 주문 저장 → COMMIT
변경 후:  쿠폰 소모 → 주문 저장 → 재고 차감 → COMMIT
```

**개선 전**

```kotlin
// 0 행은 재고 부족과 상품 소멸을 함께 뜻한다.
sorted.forEach { item ->
    if (!productService.decreaseStock(item.productId, item.quantity.value)) {
        throw CoreException(ErrorType.CONFLICT, "[productId = ${item.productId}] 재고가 부족합니다.")
    }
}

return OrderInfo.of(
    orderService.place(
        userId = user.id,
        items = items,
        discountAmount = discountAmount,
        usedCouponId = applied?.userCouponId,
    ),
)
```

**개선 후**

```kotlin
val order = orderService.place(
    userId = user.id,
    items = items,
    discountAmount = discountAmount,
    usedCouponId = applied?.userCouponId,
)

// ⚠️ OrderInfo 변환을 재고 차감보다 반드시 먼저 한다.
val orderInfo = OrderInfo.of(order)

sorted.forEach { item ->
    if (!productService.decreaseStock(item.productId, item.quantity.value)) {
        throw CoreException(ErrorType.CONFLICT, "[productId = ${item.productId}] 재고가 부족합니다.")
    }
}

return orderInfo
```

### 정합성은 그대로다

재고 차감이 실패하면 `CoreException`이 트랜잭션 전체를 롤백시킨다. 주문 행도 항목 행도 남지 않는다. `@Transactional`의 기본 동작이다.

### 이 변경에서 가장 위험한 줄

`OrderInfo.of(order)`를 차감보다 **먼저** 부르는 저 한 줄이다.

```kotlin
@Modifying(clearAutomatically = true, flushAutomatically = true)
fun decreaseStock(...): Int
```

`decreaseStock`은 호출될 때마다 **영속성 컨텍스트를 통째로 비운다.** 주문을 먼저 저장해 두면, 그 `clear()`로 방금 저장한 `OrderModel`이 detach된다. 그 뒤에 `order.items`를 읽으면 컬렉션 초기화 여부에 따라 깨진다.

"변환은 마지막에 하는 게 자연스럽다"며 이 순서를 되돌리면 **조용히 깨진다.** 그래서 코드에도 경고 주석을 남겼다.

### 롤백이 처음으로 진짜 방어선이 되었다

변경 전에는 재고 차감이 먼저라 실패하면 **주문 저장에 도달조차 하지 않았다.** 롤백은 형식적이었다. 변경 후에는 이미 INSERT된 주문 행을 롤백이 **실제로 걷어내야 한다.**

즉 이 개선은 새로운 위험을 만든다. 그래서 통합 테스트에 단언을 추가했다.

```kotlin
assertThat(orderJpaRepository.count())
    .describedAs("롤백되어 주문 행이 남지 않아야 한다")
    .isEqualTo(0L)
```

이 단언이 없으면 그 회귀를 잡을 테스트가 남지 않는다.

## 4. 개선 B — FK 소유권을 자식으로 옮긴다

2장에서 발견한 정체불명의 `UPDATE order_items SET order_id`. 이건 매핑이 만든 쿼리다.

**개선 전** — `OrderModel`이 단방향 `@OneToMany` + `@JoinColumn`으로 FK를 소유한다.

```kotlin
// OrderModel
@OneToMany(cascade = [CascadeType.ALL], orphanRemoval = true, fetch = FetchType.LAZY)
@JoinColumn(name = "order_id", nullable = false)
private val orderItems: MutableList<OrderItemModel> = items.toMutableList()

// OrderItemModel — 자신이 어느 주문에 속하는지 모른다
```

자식이 부모를 모르는 채로 저장이 시작된다. 그래서 Hibernate는 자식을 `order_id` 없이 INSERT한 뒤, FK를 채우는 UPDATE를 **따로 발행한다.**

**개선 후** — FK 소유자를 자식으로 넘긴다.

```kotlin
// OrderItemModel — FK 소유자가 된다
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "order_id", nullable = false)
lateinit var order: OrderModel
    protected set

/** OrderModel.create 안에서만 부른다. */
internal fun assignOrder(order: OrderModel) {
    this.order = order
}

// OrderModel — 매핑의 주인 자리를 넘긴다
@OneToMany(mappedBy = "order", cascade = [CascadeType.ALL], orphanRemoval = true, fetch = FetchType.LAZY)
private val orderItems: MutableList<OrderItemModel> = items.toMutableList()
```

그리고 `OrderModel.init` **끝에서** 연관을 맺는다.

```kotlin
init {
    // ... 검증 ...
    orderItems.forEach { it.assignOrder(this) }
}
```

이제 INSERT문에 `order_id`가 바로 실리고, 뒤따르던 UPDATE가 사라진다.

### 애그리거트 경계는 바뀌지 않았다

`OrderItemModel`은 여전히 `OrderModel`의 내부 구성요소다. 바뀐 것은 **어느 쪽이 FK 컬럼을 소유한다고 JPA에 선언하는가**뿐이다. 생명주기는 여전히 `cascade = ALL` + `orphanRemoval`이 지배하고, `order_items`를 독립적으로 조회하는 경로는 만들지 않았다.

캡슐화를 지키려고 둔 장치가 셋 있다.

- 세터를 `protected`로 막고 `internal fun assignOrder` 하나로만 채운다. 항목이 다른 주문으로 옮겨갈 유스케이스가 없기 때문이다 — 이 연관은 조립 시점에 한 번만 맺힌다.
- Kotlin에 package-private이 없어 `internal`이 낼 수 있는 가장 좁은 가시성이다.
- **`data class`로 만들지 않는다.** `toString`/`equals`/`hashCode`가 자동 생성되면 `order`를 되짚다 `order.items`와 서로를 무한히 되풀이해 재귀에 빠진다.

`init` 블록에서 `this`가 자식에게 새어 나가는 것도 의도된 순서다. JPA 양방향 연관관계 편의 메서드의 표준 패턴이지만, **다른 필드 초기화가 모두 끝난 뒤 실행되도록 `init` 끝에 두었다.** 이 호출을 위로 옮기면 자식이 미완성 부모를 보게 된다.

## 5. 측정 환경 — 숫자를 읽으려면 환경을 먼저 알아야 한다

성능 숫자는 환경을 모르면 아무 의미가 없다. 앱과 MySQL을 각각 컨테이너에 넣고 **CPU·메모리를 명시적으로 고정**해서 쟀다.

### 호스트

| 항목 | 값 |
|---|---|
| 기기 | Apple M2 Pro (10코어) |
| 메모리 | 16GB |
| OS | macOS 26.6.2 |

### Docker Desktop VM

| 항목 | 값 |
|---|---|
| 할당 CPU | **5** |
| 할당 메모리 | **6,144 MiB** |
| swap | 1,024 MiB |
| 가상화 | Apple Virtualization Framework + VirtioFS |
| Docker Engine / Compose | 24.0.5 / v2.20.2 |

### 컨테이너별 자원

| 컨테이너 | CPU | 메모리 | 이미지 / 설정 |
|---|---|---|---|
| **commerce-api** | **3.0** | **2GB** | `eclipse-temurin:21-jre` (OpenJDK 21.0.12+8), JVM `-Xms1g -Xmx1g` |
| **mysql** | **2.0** | **2GB** | `mysql:8.0` (실제 8.0.46, aarch64), `innodb_buffer_pool_size=1G` |

부하 도구인 k6(v2.1.0)는 **호스트에서** 돌렸다. 컨테이너에 넣으면 측정 대상과 VM 자원을 다투게 된다.

애플리케이션 설정은 Spring Boot 3.4.4 / Kotlin 2.0.20, 톰캣 워커 `max: 200`, HikariCP `maximum-pool-size: 40` / `connection-timeout: 3000ms`다.

### `deploy.resources`는 조용히 무시된다

여기에 함정이 하나 있다. Compose에서 자원을 제한할 때 이렇게 쓰면 **아무 일도 일어나지 않는다.**

```yaml
# ❌ Swarm 전용 — docker compose up 에서 경고도 에러도 없이 무시된다
deploy:
  resources:
    limits:
      cpus: "3.0"
      memory: 2g
```

```yaml
# ✅ 최상위 서비스 키로 줘야 실제로 걸린다
cpus: "3.0"
mem_limit: 2g
```

에러가 안 나기 때문에 "3코어로 제한했다"고 믿은 채 5코어를 다 쓰고 있을 수 있다. 그래서 기동 후 반드시 눈으로 확인해야 한다.

```bash
$ docker inspect loopers-loadtest-commerce-api-1 \
    --format '{{.HostConfig.NanoCpus}} {{.HostConfig.Memory}}'
3000000000 2147483648
```

JVM 쪽에서도 교차 확인이 된다.

```
Effective CPU Count: 3
CPU Period: 100000us
CPU Quota: 300000us
```

부수적으로 하나 더 드러났다. `mem_limit: 2g`만 주면 Docker가 **swap을 메모리의 2배로 자동 설정**한다(`MemorySwap=4294967296`). "2GB 제한"이 실제로는 "RAM 2GB + swap 2GB"였다. 힙을 1g로 고정했으니 이번엔 문제가 없었지만, 메모리 압박을 재는 실험이었다면 이 기본값이 결과를 조용히 바꿨을 것이다.

## 6. 측정 전에 걷어내야 했던 것들

처음 잰 숫자는 우리 코드의 성질이 아니었다. 두 가지를 먼저 걷어내야 했다.

### `show-sql`을 켠 채로 재면 로깅 처리량을 잰다

로컬 프로필은 `spring.jpa.show-sql=true`다. Hibernate가 쿼리마다 한 줄씩 stdout에 찍고, 그 줄이 Docker의 json-file 로그 드라이버를 거쳐 디스크까지 간다. 주문 1건이 쿼리 6~7개이므로 1,000 TPS면 **초당 7,000줄**이다.

껐더니 같은 조건에서 이렇게 달라졌다.

핫스팟 600 TPS 기준이다.

| 설정 | 달성 TPS | 응답 중앙값 |
|---|---|---|
| `show-sql: true` | 593.5 | **624.7ms** |
| `show-sql: false` | 600.0 | **16.5ms** |

락 경합을 재고 있다고 믿었지만 실제로는 로깅 파이프라인을 재고 있었다.

다만 이 비교는 단일 변수 A/B가 아니라는 점을 밝혀 둔다. 두 측정 사이에 `show-sql`뿐 아니라 k6의 `preAllocatedVUs`도 함께 올렸다. 누락된 반복은 애초에 요청을 만들지 않아 지연 지표에 들어가지 않으므로 VU 설정이 38배 차이를 만들 수는 없지만, **두 가지를 바꿔 놓고 하나의 원인으로 돌린 비교**인 것은 사실이다. 이 표는 방향을 보여주는 근거이지 정확한 배수의 근거는 아니다.

### "준비됐다"는 신호가 준비를 뜻하지 않았다

측정 직전에 재고를 넉넉히 주입해야 한다. 시드 재고 총합이 6,850개라 500 TPS면 14초 만에 소진되고, 그 뒤로 재는 것은 "409를 얼마나 빨리 뱉는가"이기 때문이다.

그런데 actuator health가 UP인 걸 보고 주입했더니, 실패하는 상품 ID가 33, 66, 88, 99, 110… 전부 11의 배수로 나왔다. 시더가 "11개마다 재고 0"을 넣는 바로 그 상품들이다.

**health UP은 웹 서버가 떴다는 뜻이지 `ApplicationRunner`(시더)가 끝났다는 뜻이 아니다.** 재고 주입이 시더를 앞질러 버린 것이다.

그래서 "상품 137개"를 기다리도록 고쳤는데, 이번엔 더 미묘하게 틀렸다. **이전 측정이 남긴 옛 스키마에도 상품은 137개 있다.** 앱이 테이블을 drop하기도 전에 조건이 참이 되어 옛 테이블에 주입해 버렸다.

새 스키마임을 유일하게 특정하는 조건은 이거였다.

```
상품 137개 AND 주문 0행
```

> **"준비됐는가"를 판정하는 조건이 이전 상태에서도 참일 수 있다면, 그건 판정이 아니다.**

## 8. 13%를 줄였는데 왜 3,471배가 되는가

락 구간에서 걷어낸 것은 0.183ms이고, 전체 1.41ms의 **13%**다. 산술적으로는 708 → 813 TPS 정도여야 한다. 실제로는 887 TPS가 나왔고, 700 TPS 구간의 중앙값은 8,331ms에서 2.4ms로 **3,471배** 좋아졌다.

산술 계산이 틀리는 이유는 **대기 시간이 이용률에 선형이 아니기 때문**이다.

```
평균 대기 시간 ∝ ρ / (1 - ρ)      (ρ = 이용률)

ρ = 0.95  →  대기 배수 19배
ρ = 0.80  →  대기 배수  4배
```

포화 직전 구간에서는 서비스 시간을 조금만 줄여도 ρ가 임계점 아래로 내려가면서 **대기 시간이 비선형적으로 무너진다.**

개선 전 700 TPS는 상한 708을 코앞에 둔 과포화 상태였다. 개선 후에는 상한 887 아래의 여유 구간이 되었다. 그 차이가 8,331ms와 2.4ms다.

> **동시성 최적화는 "얼마나 줄였나"가 아니라 "임계점을 넘겼나"로 평가해야 한다.**

같은 이유로, 임계점에서 멀리 떨어진 구간에서는 이 개선이 거의 보이지 않는다. 400 TPS에서 개선 전후가 똑같이 2.3ms인 것이 그 증거다. **개선이 없어서가 아니라 그 구간에서는 잴 것이 없어서다.**

## 9. 하지 않은 것

### 인프라 설정을 건드리지 않았다

락 안에서 잰 1.267ms 중 **1.084ms가 `COMMIT`**이고, 그 정체는 fsync다. `innodb_flush_log_at_trx_commit`과 `sync_binlog`를 낮추면 처리량이 크게 오른다. **그럼에도 하지 않았다.**

그것은 **내구성을 처리량과 맞바꾸는 결정**이다. 장애 시 커밋된 주문이 사라질 수 있고, 그 교환을 애플리케이션 레벨에서 임의로 할 수 없다. 무엇보다 fsync 튜닝으로 얻는 숫자는 **우리가 짠 코드의 성질을 말해주지 않는다.**

측정 환경 보정 목적으로도 쓰지 않았다. 보정하면 개선 효과가 더 선명하게 보였겠지만, 보정 없이도 상한이 +25.3% 올랐으므로 필요가 없었다.

### 낙관적 락·비관적 락을 도입하지 않았다

조건부 `UPDATE`를 유지한다. 판정과 갱신을 한 문장에 합쳐 read-check-write 틈 자체를 없애며, 낙관적 락과 달리 재시도가 없고 비관적 락과 달리 `SELECT ... FOR UPDATE` 왕복이 없다.

이번 측정이 그 선택을 뒷받침한다. **락 보유 시간이 짧다는 것이 처리량의 근거였고, 왕복을 하나 더 두는 방식이었다면 이 숫자가 나오지 않는다.**

### 커넥션 풀을 늘리지 않았다

늘리면 분산 시나리오의 상한이 올라갈 여지가 있다. 하지만 이 값은 세 앱이 공유하고, DB 코어 수를 넘는 커넥션은 컨텍스트 스위칭만 늘린다. **측정 없이 올릴 값이 아니다.**

무엇보다, 만약 측정 없이 "커넥션 풀을 늘리자"로 갔다면 **핫스팟은 708 TPS에 그대로 묶여 있었을 것이다.** 그쪽 병목은 커넥션이 아니라 락이기 때문이다.

## 10. 이 숫자들의 한계

**절대 수치는 이 환경의 것이다.** 앱 3코어·MySQL 2코어로 묶은 노트북 위 Docker의 숫자이지 프로덕션 용량이 아니다. 의미가 있는 것은 같은 조건에서 잰 **전후 비율**이다.

**환경이 바뀌면 병목도 바뀐다.** 같은 코드를 앱만 호스트에서 돌려 쟀을 때는 핫스팟 상한이 377 TPS였다. 지금은 708이다. 앱과 MySQL이 같은 브리지 네트워크에 들어오면서 DB 왕복이 짧아졌고, 그만큼 락 보유 시간도 짧아졌기 때문이다. **다른 환경의 숫자와 섞어 쓰면 안 된다.**

**부하 도구에도 상한이 있다.** 호스트 k6 → Docker published port → 톰캣 경로는 3,500 TPS를 p95 2.56ms로 소화하고 약 3,800 TPS에서 포화됐다. 측정값이 그 근처로 나온다면 그건 서버가 아니라 하네스를 잰 것이다.

**도구의 지표를 그대로 믿으면 안 된다.** k6 v2.1.0에서 `http_req_duration`의 `max`가 924초로 찍혔는데, 같은 실행의 `iteration_duration` `max`는 1.65초였다. 반복 하나가 요청 하나를 담으므로 이건 불가능하다. `max`는 오염돼 있었고, 백분위수는 두 지표가 서로 교차 검증되어 신뢰할 수 있었다. 그래서 이 글은 **`max`를 보고하지 않는다.**

**락 대기는 에러로 드러나지 않는다.** 분산 1,400 TPS에서 p95가 정확히 59,999ms였다 — k6의 기본 HTTP 타임아웃 60초다. 서버가 에러를 반환한 게 아니라 요청이 큐에 쌓인 채 클라이언트가 먼저 포기한 것이다. 커넥션은 이미 쥔 채로 락을 기다리므로 `connection-timeout`에 걸리지 않는다.

> **부하 테스트의 임계값에는 에러율뿐 아니라 반드시 응답 시간 기준을 함께 넣어야 한다.** 서버 지표만 보면 "에러 0%, 정상"인데 실제 클라이언트는 전부 타임아웃일 수 있다.

**쿠폰 경로는 재지 않았다.** 쿠폰은 1인 1매·1회 사용이라 두 번째 요청부터 409가 나 지속 부하를 걸 수 없다. `user_coupons`의 조건부 `UPDATE`가 처리량에 어떤 영향을 주는지는 이 글이 답하지 않는다.

## 마치며

이 작업에서 실제로 바꾼 코드는 짧다. 호출 순서를 옮긴 것 하나, 매핑의 주인을 바꾼 것 하나. 새 기능도 없고 새 기술도 없다.

그런데 그 두 줄에 도달하기까지 필요했던 건 전부 **측정**이었다. 병목이 커넥션이 아니라 락이라는 것도, 락 구간 안에 INSERT 3건이 들어 있다는 것도, 우리가 쓴 적 없는 UPDATE가 주문마다 나가고 있다는 것도 재기 전에는 몰랐다.

그리고 측정 자체도 두 번 틀렸다. 처음엔 로깅 처리량을 쟀고, 그다음엔 이전 측정이 남긴 데이터 위에서 쟀다. 둘 다 숫자는 멀쩡하게 나왔다. **틀린 측정은 에러를 내지 않는다.**

성능 개선에서 가장 위험한 순간은 병목을 못 찾는 때가 아니다. **찾았다고 믿는 때다.** 커넥션 풀을 늘리자는 결론은 그럴듯했고, 실제로 분산 시나리오에서는 효과가 있었을 것이다. 그리고 핫스팟은 708 TPS에 그대로 묶여 있었을 것이다.

재기 전에는 어느 쪽인지 알 수 없다.
